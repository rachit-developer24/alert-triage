# Slice 01 — Alert Ingestion

## Alert Fields

### Client-provided

sourceAlertId
- required
- identifier provided by the source vulnerability system

cveId
- required
- identifies the known vulnerability

hostname
- required
- identifies the affected network device

cvssScore
- required
- must be between 0.0 and 10.0

description
- required
- description of the vulnerability

detectedAt
- required
- time the source system detected the vulnerability


### Server-owned

id
- generated by our alert-triage service
- uniquely identifies the alert inside our system

severity
- derived from cvssScore

status
- set to NEW when the alert is first created

receivedAt
- set by our service when the alert is received


### Enriched from internal inventory

environment
- identifies whether the affected device belongs to DEV, TEST, STAGING or PROD
- obtained from trusted internal inventory using the hostname


## Severity Rules

0.0       = NONE
0.1–3.9   = LOW
4.0–6.9   = MEDIUM
7.0–8.9   = HIGH
9.0–10.0  = CRITICAL


## Duplicate Rule

Two findings are considered the same vulnerability when they have:

- the same cveId
- the same hostname

If the same vulnerability is reported again for the same hostname,
the service must not create another active alert.

The sourceAlertId is also stored so that repeated delivery of the exact
same source event can be identified.

If the same active alert already exists, the API returns HTTP 200 OK
with the existing alert instead of creating a new one.



## Scenario 1 — Valid alert is accepted

Given a valid vulnerability alert
When the client sends POST /api/alerts
Then the API returns HTTP 201 Created
And the alert is stored
And the response contains the created alert
And the response contains the server-generated id


## Scenario 2 — Invalid alert is rejected

Given an alert has a missing required field
Or cvssScore is outside the range 0.0 to 10.0
When the client sends POST /api/alerts
Then the API returns HTTP 400 Bad Request
And no alert is created


## Scenario 3 — Alerts can be listed

Given alerts have been stored
When the client sends GET /api/alerts
Then the API returns HTTP 200 OK
And the response contains the stored alerts
And alerts are returned newest first
